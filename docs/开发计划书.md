## 1. 技术路线总览（定稿）

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | 抖音小程序原生 | 非 Taro（理由见下） |
| 后端 | 抖音云开发（CloudBase） | 云函数 + 云数据库 + 云存储，免运维 |
| 内容存储 | 云存储 + CDN | 承载视频 / 音频 / 图片 |
| 电商 | 抖音精选联盟 + 小程序购物车 | 佣金带货，不自建商品体系 |
| 登录 | 抖音授权登录 | 获取基础用户信息 |
| 内容安全 | 抖音内容安全接口 + 人工审核 | 上线前强制过审 |

### 1.1 为什么前端用「原生」而非「Taro」

- V1.0 已明确只做抖音单端（多端是三期的事），Taro 的核心价值在多端复用，当前用不上。
- 原生开发对抖音特有能力（购物车、短视频挂载、抖音登录、内容安全接口）支持最直接、调试最顺。
- 性能更优、包体积更小、踩坑更少；后期真要扩微信端，再用 Taro 重构的迁移成本可控。

### 1.2 为什么后端用「云开发」

- MVP 阶段业务量小，云开发免服务器运维、按量付费、成本最低。
- 云函数 + 云数据库能覆盖「用户/关卡/进度/商品」全部数据需求。
- 后续量大了可平滑迁移到自建服务或云托管。

> **V1.1 说明**：本节及第 1 节为**定稿**口径。《需求文档》第 8.3、12 节原将「原生 vs Taro」列为待定，已统一到本口径。

## 2. 系统架构

```
抖音短视频（引流入口）
        │ 挂载
        ▼
抖音小程序（前端，原生）
        │
        ├── 内容模块（短视频 / 实验关卡 / 商品位）
        ├── 用户模块（登录 / 年龄标签 / 进度 / 打卡）
        └── 电商模块（精选联盟 / 购物车）
        │
        ▼
抖音云开发（后端）
  ├── 云函数（业务逻辑 / 接口）
  ├── 云数据库（用户 / 主题 / 内容 / 关卡 / 进度 / 商品）
  └── 云存储 + CDN（视频 / 音频 / 图片）
        │
        ▼
抖音开放平台能力（登录 / 精选联盟 / 购物车 / 内容安全）
```

### 4.1 V1.1 新增：接口契约冻结（关键路径修复）

**问题**：原计划 S2 前端与 S3 后端完全并行，但**没有任何「接口契约冻结」节点**。两侧各自开工、无人对齐 API 定义，联调期（S5，仅 2 周）大概率被接口对不上吃掉，直接冲击 M2。

**修复**：在 S1 增设交付物 **《接口契约文档》**，随 M1（10-02）与需求一并通过评审并冻结。S2/S3 必须按契约实现，契约变更走变更评审（同《需求文档》9.3 的冻结机制）。

**契约至少覆盖**：云函数名与入参/出参、数据库集合结构与字段、错误码约定、分页规范，以及埋点事件命名（见《需求文档》9.5）。

### 4.2 V1.1 调整：内容审核前置

**问题**：原计划把内容安全审核集中在 S5（联调期）。一旦审核被拒，内容重做与提审重排都发生在关键路径末端，**没有任何返工缓冲**——而原风险表里恰好承认「儿童内容审核不通过 → 无法上线」。

**修复**：拆成三道关卡，前移两道：

| 时点 | 动作 |
| --- | --- |
| S1（10-02 前） | **视频脚本先行送审**，通过后才进入制作 |
| S4（10-05 ~ 10-30） | 内容**边生产边审**，单条通过单条入库，不积压到 S5 |
| S5（10-26 ~ 11-06） | 仅做**最终整体过审**与提审，不再承担首次送审风险 |

### 4.3 V1.2 压缩：按 11-15 截止倒排（含取舍说明）

课程截止日 ≈ **2026-11-15**，而 V1.1 的终点 M4 = 11-23，**超出 8 天**，必须压缩。

**可用窗口**：09-08 ~ 11-15 = 68 天 ≈ 9.7 周。

| 项 | 原 | 现 | 压缩理由 |
| --- | --- | --- | --- |
| S2 前端开发 | 4 周 | **3 周** | 关键路径上唯一可压的开发阶段。2 人并行下必须严格按接口契约实现，减少返工 |
| S6 上线灰度 | 1.5 周 | **1 周** | 提审 + 灰度压缩到 1 周 |
| S4 内容生产 | 4 周 | 4 周（**不变**） | **不在关键路径**（并行于 S2），压它一天也省不出总工期 |
| S1 设计 | 1.5 周 | 1.5 周（**不变**） | 设计压不得——压掉的时间会以返工形式在 S2 还回来 |
| S5 联调测试 | 2 周 | 2 周（**不变**） | 联调是最易超期的阶段，已有接口契约托底，但仍不宜再压 |

> ⚠️ **缓冲风险（务必知悉）**
>
> 压缩后 M4 = **2026-11-13（周五）**，距截止日 **仅 2 天缓冲**。这意味着**关键路径上任一处超期，都会直接顶到截止日**，且 M3→M4 之间没有余量。
>
> **建议**：把交付终点从 M4「正式上线灰度」改为 **M3「功能可用 + 通过内容安全审核」（2026-11-06）**。理由——课程作业通常不要求小程序**真实发布上线**，能达到「可运行、可演示、可提交」即可。如此缓冲由 **2 天增至 9 天**。
>
> **待确认**：本课程的交付要求是否包含「真实发布上线」？若否，以 **M3 = 11-06** 为交付终点。**在此项确认前，两条终点都保留在表中。**

## 7. 关键风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 儿童内容审核不通过 | 无法上线 | **V1.1**：脚本 S1 先审、S4 边产边审、S5 只做最终过审（见 4.2） |

| 前后端并行无接口契约（V1.1） | 联调返工、M2 延期 | S1 产出接口契约文档，随 M1 冻结，S2/S3 按契约实现（见 4.1） |

| **关键路径缓冲仅 2 天**（V1.2 新增） | 任一处超期即顶到截止日 | 交付终点按 **M3（11-06）** 而非 M4（11-13）；S2/S3 严格按契约实现以压缩 S5 返工；**建议取消 S6 或将其移出截止日内** |
